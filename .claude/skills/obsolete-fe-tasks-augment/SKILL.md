## User Input

```text
$ARGUMENTS
```

You **MUST** consider the user input before proceeding (if not empty).

Supported arguments:
- *(no argument)* / `--refresh` — default. Append missing FE tasks, leave existing FE tasks untouched. Idempotent. This is the mode used by the automatic `after_tasks` hook.
- `--force` — discard every FE-classified task (heuristic: task description contains `frontend/src/`) and regenerate from scratch. Manual invocation only. Never passed by the hook.

Any other value is treated as ignored noise.

## Purpose

`/speckit-tasks` (vendored skill) generates the backend task plan from `plan.md` and `data-model.md`. It is not aware of the FE↔BE contract negotiated in Etap 2 and produces no per-component frontend tasks.

This skill closes that gap. It reads:
- the `Scope:` and `FE Surface:` block emitted by `product-strategist` into `spec.md`;
- the endpoint table in `specs/{feature}/api-contract.md`;
- the existing `specs/{feature}/tasks.md`;

and emits one FE task per component listed in `FE Surface:`, plus a single global api-client regen task (foundational, sequenced at the start of the FE Wave) and one routes task per feature. Backend tasks generated by the vendored skill are never touched.

The output is consumed downstream by `plan-validator` (CHECK 8 endpoint coverage, CHECK 10 FE Surface parity) and by `fe-component-writer` / `fe-route-writer`.

## Pre-Execution Checks

**Determine active feature**:
- Run `.specify/scripts/powershell/setup-plan.ps1 -Json` from repo root and parse `FEATURE_SPEC`, `IMPL_PLAN`, `SPECS_DIR`, `BRANCH`.
- If the script fails or `BRANCH` does not look like a feature branch (no `NNN-` prefix), abort with a clear error message.

**Verify required artefacts exist**:
- `FEATURE_SPEC` (`specs/{feature}/spec.md`) — required. Abort if missing: `ERROR: spec.md missing — run /speckit-specify first`.
- `{SPECS_DIR}/api-contract.md` — required. Abort if missing: `ERROR: api-contract.md missing — run /speckit-plan (which triggers /api-contract-emit) first`.
- `{SPECS_DIR}/tasks.md` — required. Abort if missing: `ERROR: tasks.md missing — run /speckit-tasks first`.

**Scope early-exit**:
- Parse the `Scope:` literal from the handoff section of `spec.md`. Accepted values: `fe-only`, `be-only`, `both`, `direct-edit`.
- If `Scope: be-only` → emit exactly:
  ```
  FE-TASKS-AUGMENT SKIPPED — Scope is be-only
  File: specs/{feature}/tasks.md (unchanged)
  ```
  and return immediately.
- If `Scope: direct-edit` → abort with: `ERROR: Scope is direct-edit — no SpecKit artefacts expected. fe-tasks-augment must not run.`
- If `Scope:` field is missing or has an unexpected value → abort with: `ERROR: spec.md Scope field missing or invalid. Inspect manually.`

**Mode selection**:
- Default mode: `refresh` (append-or-skip-existing).
- `--force` flag → mode: `force` (regenerate all FE-classified tasks; backend tasks preserved).

**Automatic hook constraint**:
- When invoked through `extensions.yml` `after_tasks` hook, `--force` is **never** passed. Hook always operates in `refresh` mode.

## Outline

1. **Setup**: parse the setup-plan JSON; resolve `FEATURE_SPEC`, `SPECS_DIR`, and `tasks.md` absolute paths.

2. **Load context**:
   - Read `spec.md` in full — locate the handoff section (`Scope:` literal + optional `FE Surface:` block + optional `Design artifact:` line).
   - Read `api-contract.md` in full — parse the endpoint table in section `## 1. Endpoints`.
   - Read `tasks.md` in full — index existing tasks by description path to detect collisions.

3. **Derive FE component inventory**:
   - **Primary source**: every component literally enumerated under `FE Surface:` in `spec.md`. Honour the structure (page → panels → modals).
   - **Routes**: one task per feature directory (`frontend/src/app/features/{feature}`) implied by the page component(s).
   - **api-client**: exactly one global task per run (sequenced as the first FE task in the FE Wave).
   - **Store tasks**: never auto-generated. Emit a WARNING block instead (see step 6).
   - **CRUD modal heuristic**: explicitly disabled. Do not infer modals from endpoint names. Only components named in `FE Surface:` become tasks.

4. **Derive consumer mapping (per component)**:
   - For each component task, look up endpoints in `api-contract.md` whose `Consumer` column references that component (matched by literal class name or selector).
   - Emit `Consumes: METHOD /route` for the first matched endpoint; concatenate multiple endpoints with `; ` separator. If no endpoint references the component, emit `Consumes: —` (em dash).
   - The literal token `Consumes:` is load-bearing — `plan-validator` CHECK 8 parses it.

5. **Derive dependencies**:
   - Every component task depends on the api-client task (foundational).
   - The routes task for a feature depends on every component task in that feature.
   - Component-to-component dependencies (e.g. modal depends on its host page) are emitted only when the FE Surface block makes the nesting explicit.
   - BE-side dependencies are recorded as a non-enforced `Requires:` note (e.g. `Requires: T0XX (handler for GET /resources)`), separate from `Depends on:`. `plan-validator` does not parse `Requires:`.

6. **Update `tasks.md`**:
   - **Refresh mode**:
     - For each derived FE task, check whether a task already exists whose description references the same `frontend/src/...` path. If it exists, skip silently. Otherwise append the task to the FE Wave section, preserving the numbering sequence from existing tasks.
     - Append the WARNING block(s) defined below if not already present (matched by their literal heading).
   - **Force mode**:
     - Delete every existing FE-classified task (description contains `frontend/src/`). Renumber remaining (backend) tasks if and only if numbering became non-contiguous; otherwise leave numbering as-is and continue from the highest existing number for FE tasks.
     - Append the freshly derived FE task set and WARNING block(s).
   - Ensure the api-client task is the **first** FE task in document order. Renumber FE tasks accordingly when in `force` mode.

7. **Sanity check**:
   - Verify every generated FE task description literally contains the substring `frontend/src/`. If a generated task fails this check, abort with: `ERROR: generated FE task missing frontend/src/ path — refusing to write tasks.md (plan-validator CHECK 10 would mis-classify).`

8. **Report**: print the target absolute path, the mode (`refresh` / `force`), the number of FE tasks newly added, the number of FE tasks skipped (refresh mode), and the warnings emitted. End with:
   ```
   FE-TASKS-AUGMENT COMPLETE
   File: specs/{feature}/tasks.md
   Scope: {fe-only|both}
   Mode: {refresh|force}
   FE tasks added: {N}
   FE tasks skipped (already present): {M}
   Warnings emitted: {K}
   ```

## FE task format

Every FE task written by this skill follows this exact shape:

```
- [ ] T0NN [USx] [FR-...] Implement `ClassName` at `frontend/src/app/features/{feature}/{path}` — {short description}. Consumes: {METHOD /route | —}. Depends on: T0XX[, T0YY].
```

Notes on the format:
- The `[FE]` marker is intentionally **not** present. Classification is path-based (`frontend/src/`).
- `Consumes:` is mandatory. Use the em dash `—` for purely presentational components.
- `Depends on:` is mandatory. Use `Depends on: T0XX` (api-client task ID) at minimum for every component task. Page tasks may add more.
- `Requires:` (BE handler dependency) is optional and emitted on a new line indented two spaces under the task when relevant. It is documentation, not enforced.

### Worked examples

api-client (foundational, always first FE task in the wave):
```
- [ ] T030 [US1] [FR-001] Regenerate TypeScript HTTP client at `frontend/src/app/api/` from `specs/{feature}/swagger.json`. Consumes: —. Depends on: —.
```

Page component:
```
- [ ] T031 [US1] [FR-002] Implement `ResourceListPageComponent` at `frontend/src/app/features/resources/pages/resource-list-page` — lists resources with pagination. Consumes: GET /resources. Depends on: T030.
  Requires: T012 (handler for GET /resources).
```

Modal component:
```
- [ ] T033 [US1] [FR-003] Implement `ResourceFormModalComponent` at `frontend/src/app/features/resources/modals/resource-form-modal` — create/edit resource. Consumes: POST /resources; PUT /resources/{id}. Depends on: T030, T031.
```

Routes:
```
- [ ] T035 [US1] [FR-002] Create `resources.routes.ts` at `frontend/src/app/features/resources/resources.routes.ts` and register in `app.routes.ts`. Consumes: —. Depends on: T031, T032, T033.
```

## WARNING blocks

The skill emits two WARNING blocks at the bottom of the FE Wave section. Each block is idempotent — re-runs in `refresh` mode skip the block if its literal heading is already present.

**WARNING — endpoints without a matching screen**:
- Triggered when `api-contract.md` lists at least one endpoint marked `NEW` (new in this feature) whose `Consumer` column does not match any component derived from `FE Surface:`.
- Format:
  ```
  > **WARNING — endpoints without a matching screen.** The following NEW endpoints have no FE component declared in `FE Surface:`. They likely need a modal or page that the developer must add manually. The CRUD-modal heuristic is intentionally disabled in this skill.
  >
  > - POST /resources (no consumer in FE Surface)
  > - DELETE /resources/{id} (no consumer in FE Surface)
  ```

**WARNING — shared state**:
- Triggered when the feature contains more than one FE component (excluding api-client and routes).
- Format:
  ```
  > **WARNING — shared state.** If multiple components in this feature share state, add a `{Feature}Store` task explicitly. This skill does not generate store tasks automatically.
  ```

## Hook integration

Register this skill in `.specify/extensions.yml` under `hooks.after_tasks` as a **mandatory non-optional** entry (`enabled: true`, `optional: false`, `condition: null`). The hook runs automatically after `/speckit-tasks` returns, in `refresh` mode (no `--force`). Manual invocation via `/fe-tasks-augment --force` is reserved for the developer when intentionally regenerating FE tasks after a contract or FE Surface change.

## Key rules

- Use absolute paths for filesystem operations; use project-relative paths inside the emitted markdown.
- Backend tasks (no `frontend/src/` in description) are never modified — neither in `refresh` nor in `force` mode.
- Every generated FE task must contain the literal substring `frontend/src/` in its description. This is a hard sanity check (step 7) because `plan-validator` CHECK 10 classifies tasks by that substring.
- `Consumes:` is the only literal token coupled to `plan-validator` CHECK 8. Do not paraphrase.
- The CRUD-modal heuristic is **disabled by design**. Surfacing unmatched endpoints via a WARNING block is the contract with the developer.
- Store tasks are **disabled by design**. The WARNING block delegates the decision to the developer.
- This skill performs no git operations and no further agent calls. It is a pure file augmenter.
- Known limitation, deferred to Etap 3: `plan-validator` FE Wave is flat — sub-waves derived from FE→FE `Depends on:` chains are not honoured by the EXECUTION MAP yet.
